## 2. 为什么需要声明式语言

### 2.1 从参数驱动到意图驱动

传统 GNN explanation 系统通常以如下方式使用：

- 调用某个解释算法脚本；
- 传入目标节点、层号、阈值、候选子图大小等参数；
- 手工决定对单节点、多节点还是全测试集执行；
- 再手工比较结果、过滤结果、复用中间结果。

这种方式的问题在于，用户表达的是一串执行步骤，而不是一个稳定的分析意图。  
声明式语言的价值在于把“怎么做”尽量从用户侧移走，让用户直接描述“想看什么”。

例如：

```text
EXPLAIN ALL WHERE FACTUAL = TRUE COMPARE BY COMMON_NODES
```

这条查询表达的是：

- 目标是全部测试节点；
- 只关心 factual explanation；
- 希望对结果做共性结构分析。

它并不要求用户显式指定：

- 该走单节点执行还是批量执行；
- 是否需要缓存复用；
- 是否应该触发近似执行；
- 比较阶段如何组织结果对象。

这正是 declarative system 的核心思想：  
用户声明分析目标，系统决定执行路径。

### 2.2 为什么 GUI 或逐步点击不足以替代

对于 explanation analytics 这类 workload，GUI 可以展示结果，但很难自然表达以下需求：

- 集合级目标：
  - “解释所有 test nodes”
  - “解释某一类标签对应的全部节点”
- 结果级过滤：
  - “只保留 fidelity_plus 大于某阈值的 explanation”
- 结构约束：
  - “解释中必须包含节点 517 和 516”
  - “解释中必须排除节点 8”
- 比较与聚合：
  - “比较所有 explanation 中 fidelity_plus 最好的结果”
  - “找出在结果集中反复出现的公共节点模式”
- 会话内复用：
  - “先把一个结果集命名，再在其上继续过滤、排序、比较”

这些需求具有三个典型特征：

- 它们是组合性的，而非单步交互性的。
- 它们针对的是结果集合，而非单个可视化对象。
- 它们更接近查询优化问题，而不是页面导航问题。

因此，从研究和系统实现上看，声明式语言并不是 GUI 的替代品，而是 explanation workload 的正式抽象层。


## 3. SliceGX 当前声明式层的系统定位

当前仓库中的声明式能力可以分为两层。

### 3.1 配置声明层

基于 Hydra 与 YAML 的配置系统负责声明：

- 数据集；
- 模型；
- 算法默认参数；
- 运行环境。

代表文件包括：

- [config/config.yaml](/home/ycb/SliceGX/config/config.yaml:1)
- [config/models/gcn.yaml](/home/ycb/SliceGX/config/models/gcn.yaml:1)

这一层解决的是“系统默认设置如何定义”的问题。

### 3.2 查询声明层

基于 DSL 的查询系统负责声明：

- 解释目标是谁；
- 结果需要满足什么性质；
- 是否指定层范围；
- 是否施加结构约束；
- 是否请求比较/聚合；
- 是否覆盖默认执行参数；
- 是否仅查看计划而不真正执行。

这一层主要由以下模块支撑：

- 查询入口：[slicegx_lang.py](/home/ycb/SliceGX/slicegx_lang.py:1)
- 查询表示与解析：[query_parser.py](/home/ycb/SliceGX/query_parser.py:1)
- 查询合法性校验：[query_validator.py](/home/ycb/SliceGX/query_validator.py:1)
- 结果对象：[result_schema.py](/home/ycb/SliceGX/result_schema.py:1)

如果用更学术的表述，可以说当前 SliceGX 正在形成一个面向 GNN explanation analytics 的 declarative query interface。


## 4. 语义对象与形式化视角

为了把语言说清楚，需要先定义它操作的对象。

### 4.1 基本对象

令：

- `G` 表示输入图及其节点、边、特征、标签等数据；
- `T` 表示目标节点集合；
- `q` 表示一条声明式查询；
- `E(t)` 表示针对目标节点 `t` 生成的 explanation result；
- `R` 表示查询执行后得到的 explanation result set；
- `C` 表示对 `R` 做比较或聚合后得到的 comparison summary；
- `P` 表示 query planner 生成的计划对象。

### 4.2 当前结果对象

从实现上看，一个 explanation result 当前至少包含：

- `node_id`
- `nodes`
- `factual`
- `counterfactual`
- `both`
- `score`
- `fidelity_plus`
- `fidelity_minus`
- `layer`

对应实现见 [result_schema.py](/home/ycb/SliceGX/result_schema.py:1) 中的 `ExplanationResult`。

一个完整查询执行结果 `QueryExecutionResult` 当前包含：

- 原始查询摘要；
- 选用算法；
- 逻辑/物理计划摘要；
- 结果总数与过滤后结果数；
- explanation results；
- comparison summary；
- 时间统计；
- cache 统计；
- 错误信息；
- 执行元信息摘要。

这说明当前系统已经不只是“跑完打印若干节点”，而是开始具备 formal result model 的雏形。

### 4.3 查询的总体语义流程

对一条普通查询，当前可将其语义流程概括为：

1. 目标解析：从 `EXPLAIN` 子句确定目标集合 `T`。
2. 参数合并：将 query 中的覆盖参数与配置默认值合并。
3. 计划生成：根据目标范围、层范围、近似模式等形成执行计划。
4. explanation 生成：对 `T` 中目标执行 explanation。
5. 结果过滤：应用 `WHERE` 条件得到结果集 `R`。
6. 比较或聚合：若存在 `COMPARE BY`，则由 `R` 导出 `C`。

## 5. 当前语法结构

### 5.1 核心骨架

当前语言的核心查询形态可表述为：

```text
EXPLAIN <TARGET>
[WHERE <PREDICATE>]
[AT LAYER <n> | AT ALL LAYERS]
[INCLUDE <NODE_LIST>]
[EXCLUDE <NODE_LIST>]
[COMPARE BY <COMPARE_METRIC>]
[WITH <PARAM> <VALUE>]
```

此外还支持：

- `LET <name> = <expr>`
- `FILTER <name> WHERE ...`
- `RANK <name> BY FIDELITY_PLUS`
- `COMPARE <name> BY ...`

形式化语法细节见 [query_language_spec.md](/home/ycb/SliceGX/docs/query_language_spec.md:1)。

### 5.2 目标子句

当前支持四类目标：

- `EXPLAIN NODE <id>`
- `EXPLAIN NODES <id1>,<id2>,...`
- `EXPLAIN ALL`
- `EXPLAIN CLASS <label>`

其中：

- `NODE` 与 `NODES` 面向单点或给定集合解释；
- `ALL` 面向全测试集解释；
- `CLASS` 面向类别级分析。

这使语言天然具有集合级 workload 表达能力，而不是只围绕单节点查询设计。

### 5.3 结果谓词

当前 `WHERE` 支持的谓词包括：

- `FACTUAL = TRUE | FALSE`
- `COUNTERFACTUAL = TRUE | FALSE`
- `FIDELITY_PLUS > x`
- `FIDELITY_MINUS < x`
- `SUBGRAPH_SIZE <= x`

需要特别指出的是：  
当前 `WHERE` 的语义是结果过滤语义，而非前置搜索约束语义。也就是说，系统先生成 explanation result，再按谓词筛选。

### 5.4 层级范围

当前支持：

- `AT LAYER <n>`
- `AT ALL LAYERS`

这使查询不再局限于“给一个节点求一个解释”，而可以显式表达 layer-wise explanation workload。

### 5.5 结构约束

当前支持：

- `INCLUDE <NODE_LIST>`
- `EXCLUDE <NODE_LIST>`

它们用于约束 explanation 中必须出现或不能出现的节点，从而提升研究者对结构性假设的表达能力。

### 5.6 比较与聚合

当前支持：

- `COMPARE BY FIDELITY_PLUS`
- `COMPARE BY COMMON_NODES`

其意义分别是：

- 前者强调按保真度指标选优；
- 后者强调从结果集中提取公共结构模式。

这说明当前语言已经不只是 explanation generation language，也开始具备 explanation analytics language 的属性。

### 5.7 参数覆盖与近似执行

当前支持通过 `WITH` 覆盖默认参数：

- `WITH K <int>`
- `WITH H <float>`
- `WITH THETA <float>`
- `WITH GAMMA <float>`
- `WITH APPROXIMATE <ratio>`

其中 `WITH APPROXIMATE` 的作用尤其重要。  
它反映的是执行偏好，而不是逻辑意图本身，即：

- 查询仍然要求“得到这一类 explanation result”；
- 只是系统被允许采用近似采样来降低代价。

### 5.8 会话级组合查询

当前 REPL 中支持：

- `LET`
- `FILTER`
- `RANK`
- `COMPARE <name> BY ...`

这部分能力意味着系统已经具有非常轻量但真实存在的 result algebra 雏形。  
用户可以先生成结果集，再在其上做后处理，而不必重复执行底层 explanation 算法。


## 6. 当前这套声明式语言已经能做什么

结合 [slicegx_lang.py](/home/ycb/SliceGX/slicegx_lang.py:1)、[query_parser.py](/home/ycb/SliceGX/query_parser.py:1)、[query_validator.py](/home/ycb/SliceGX/query_validator.py:1) 与 [test_features.sh](/home/ycb/SliceGX/test_features.sh:1)，当前系统已落地的能力可以概括为七类。

### 6.1 单节点与多节点解释

示例：

```text
EXPLAIN NODE 519
EXPLAIN NODES 519,537,556
```

含义：

- 前者请求对单个节点生成 explanation；
- 后者请求对一个显式节点集合批量生成 explanation。

### 6.2 全集与类别级解释

示例：

```text
EXPLAIN ALL
EXPLAIN CLASS 1
```

含义：

- 前者面向当前 test set 的全部可解释目标；
- 后者面向某一标签类别的全部目标。

这一能力非常重要，因为它让系统可以表达数据分析式 workload，而不仅是 case study 式 workload。

### 6.3 结果过滤

示例：

```text
EXPLAIN ALL WHERE FACTUAL = TRUE
EXPLAIN ALL WHERE FIDELITY_PLUS > 0.5
EXPLAIN NODE 519 WHERE SUBGRAPH_SIZE <= 6
```

含义：

- 对 explanation result set 施加语义约束；
- 以声明方式筛选“哪类解释值得保留”。

### 6.4 结构先验表达

示例：

```text
EXPLAIN NODE 519 INCLUDE 517,516
EXPLAIN NODE 519 EXCLUDE 8,517
```

含义：

- 前者要求结果中必须含有给定节点；
- 后者要求结果中不得包含给定节点。

这对于验证 motif 假设、排除干扰结构、进行受控实验很有价值。

### 6.5 集合级比较与公共模式发现

示例：

```text
EXPLAIN ALL WHERE FACTUAL = TRUE COMPARE BY FIDELITY_PLUS
EXPLAIN ALL COMPARE BY COMMON_NODES
```

含义：

- 第一条查询寻找结果集中 fidelity 更优的 explanation；
- 第二条查询寻找 explanation 集合中的公共节点模式。

这一步把系统从“生成解释”推向“分析解释”。

### 6.6 会话内组合查询

示例：

```text
LET Q1 = EXPLAIN ALL WHERE FACTUAL = TRUE
LET Q2 = FILTER Q1 WHERE FIDELITY_PLUS > 0.5
LET Q3 = RANK Q2 BY FIDELITY_PLUS
COMPARE Q3 BY COMMON_NODES
```

含义：

- `Q1` 保存基础结果集；
- `Q2` 对其做进一步过滤；
- `Q3` 对其排序；
- 最后在排序结果上做模式比较。

这说明当前系统已经支持“结果集作为一等对象”的初步工作流。


## 7. 语义与执行的分离

从学术表述上说，当前 SliceGX 最值得强调的一个特点是：  
它正在形成逻辑意图与物理执行分离的结构。

### 7.1 逻辑层

逻辑层回答的是：

- 解释谁；
- 保留什么结果；
- 是否比较结果；
- 是否施加结构性约束。

这些内容主要由 `EXPLAIN`、`WHERE`、`INCLUDE`、`EXCLUDE`、`COMPARE BY` 描述。

### 7.2 物理层

物理层回答的是：

- 选用哪种执行路径；
- 是否触发缓存复用；
- 是否采用近似采样；
- 如何组织底层执行。

这些内容主要体现在：

- `WITH APPROXIMATE`
- 自动路由到 `SS / MS / MM`

这一区分非常重要，因为 declarative system 的论文价值通常就建立在这种分层之上。


## 8. 当前实现边界与应谨慎表述之处

为了保证文档与代码一致，下面这些边界需要明确写出来。

### 8.1 `WHERE` 当前只支持单个 predicate

虽然文档层面已经按可扩展语言设计，但当前 parser 实现仍以单谓词为主，尚未支持更一般的布尔组合。

### 8.2 `RANK` 当前只支持 `FIDELITY_PLUS`

组合查询中的排序功能目前仍较轻量。

### 8.3 当前 result algebra 仍是雏形

系统已经支持命名、过滤、排序、比较，但还没有形成更完整的关系式结果代数或更丰富的聚合操作集合。

### 8.4 当前系统更适合表述为“declarative prototype with optimizer seeds”

如果面向高水平系统论文，比较稳妥的说法是：

- 已经有明确 DSL；
- 已经有基础语义与结果模型；
- 已经出现 planner / optimizer 的原型形态；
- 但 formal semantics、cost model 与 benchmark 体系仍需继续加强。

## 10. 代表性查询示例

### 10.1 单节点解释

```text
EXPLAIN NODE 519
```

意义：请求对目标节点 519 生成 explanation。

### 10.2 指定结构先验

```text
EXPLAIN NODE 519 INCLUDE 517,516 WITH K 6
```

意义：在控制子图规模参数的同时，要求 explanation 必须包含给定节点。

### 10.3 结果质量过滤

```text
EXPLAIN ALL WHERE FIDELITY_PLUS > 0.5
```

意义：对全测试集生成 explanation，并只保留高 fidelity 的结果。

### 10.4 类别级公共模式分析

```text
EXPLAIN CLASS 1 COMPARE BY COMMON_NODES
```

意义：对类别 1 的全部目标做 explanation，并分析公共结构模式。

### 10.5 近似执行

```text
EXPLAIN NODE 556 WITH APPROXIMATE 0.3
```

意义：保持逻辑查询意图不变，但允许系统以 30% 采样比例执行近似求解。

### 10.6 组合查询工作流

```text
LET Q1 = EXPLAIN ALL WHERE FACTUAL = TRUE
LET Q2 = FILTER Q1 WHERE FIDELITY_PLUS > 0.5
RANK Q2 BY FIDELITY_PLUS
```

意义：把 explanation result set 当作可复用对象进行后续分析。


## 11. 小结

综合当前仓库中的代码、测试与文档，可以对 SliceGX 当前声明式层做出如下判断：

- 它已经不是简单的命令行参数包装，而是一套初步成形的声明式查询接口。
- 它已经覆盖从目标指定、结果过滤、结构约束到比较分析的一条完整查询链路。
- 它已经体现出 declarative system 的关键思想：逻辑意图与物理执行分离。
- 它已经能够支持集合级 explanation analytics，而不仅是单点 explanation 生成。
- 它仍然是一个正在走向完整 declarative engine 的原型系统，后续仍需补强 formal semantics、优化器理论与系统级 benchmark。

如果要用一句更凝练的话概括当前阶段，可以表述为：

“SliceGX 已经具备面向 GNN explanation workload 的声明式查询雏形，并开始把 explanation 从算法调用问题提升为可分析、可规划、可组合的查询处理问题。”

# SliceGX 声明式系统下一步实现文档

## 文档目标

本文档基于 [TKDE_VLDBJ_declarative_gap_analysis.md](/home/ycb/SliceGX/docs/TKDE_VLDBJ_declarative_gap_analysis.md:1) 的差距分析，给出一份面向工程落地的中文版实现计划。

它回答的问题不是“论文里还缺什么概念”，而是：

1. 下一步应该先做哪些模块。
2. 每个模块的目标、产出和验收标准是什么。
3. 哪些改动属于必须项，哪些属于增强项。
4. 如何把现有原型逐步推进到更像 `TKDE / VLDBJ` 风格的 declarative system。


## 当前系统定位

### 当前已经具备的能力

仓库当前已经有一套可运行的声明式原型，核心包括：

- 配置声明层：
  - Hydra + OmegaConf + YAML
  - 位置见 [config/config.yaml](/home/ycb/SliceGX/config/config.yaml:1)、[config/datasets/tree_cycle.yaml](/home/ycb/SliceGX/config/datasets/tree_cycle.yaml:1)、[config/models/gcn.yaml](/home/ycb/SliceGX/config/models/gcn.yaml:1)
- 查询声明层：
  - `slicegx_lang.py` 中的 DSL
  - 支持 `EXPLAIN`、`WHERE`、`INCLUDE`、`EXCLUDE`、`COMPARE`、`WITH`、`AT LAYER`
  - 支持 `EXPLAIN PLAN FOR ...` 与 `--plan-only`
  - 支持 REPL 内 `LET / FILTER / RANK / COMPARE <name>`
- 执行层：
  - `SliceGX.py`、`Slice_MS.py`、`Slice_MM.py`
  - 支持 `SS / MS / MM` 三类执行路径
- 轻量优化能力：
  - 自动路由
  - 缓存复用
  - approximate 模式
- 组合查询能力：
  - 命名结果
  - 对已保存结果的过滤、排序、比较
- 功能验证脚本：
  - [test_features.sh](/home/ycb/SliceGX/test_features.sh:1)

### 已完成的阶段性落地

目前已经实际落地并跑通的内容包括：

- 语言规范文档
- 查询语义文档
- 轻量 optimizer 与 `EXPLAIN PLAN`
- 统一 result schema 雏形
- parser / validator / optimizer / plan-only 测试骨架
- 最小 compositional query：
  - `LET`
  - `FILTER`
  - `RANK`
  - `COMPARE <name> BY ...`

### 当前的核心短板

如果目标是面向高水平系统论文，目前最明显的问题是：

- 语言已经有了，但语义没有正式定义
- 执行器已经有了，但 planner / optimizer 还很弱
- 查询可以执行，但缺少 formal result model
- 功能可以 demo，但缺少系统级 benchmark 和 evaluation
- 当前更像“带 DSL 的原型系统”，还不像“完整 declarative engine”
- 当前组合查询仍然较轻量，尚未形成更完整的 result algebra


## 总体开发原则

下一步实现建议遵循三个原则。

### 原则 1：先补结构，再补 feature

不要优先继续加零散关键字。
优先把下面这些骨架补齐：

- 统一数据模型
- 查询语义模型
- planner / optimizer 框架
- result schema
- benchmark workload

### 原则 2：先做“论文必须项”，再做“锦上添花项”

必须项优先级高于 fancy feature。  
例如：

- formal grammar 比新增一个 `GROUP BY` 更重要
- plan abstraction 比新增一个 `WITH XXX` 更重要
- 基准 workload 比 UI 更重要

### 原则 3：每个阶段都要能被验证

每一阶段都要有：

- 明确输出
- 可测试入口
- 可被论文引用的结果


## 开发总路线图

建议分成 5 个阶段推进。

1. 语言与语义重构
2. 执行计划与优化器重构
3. 结果模型与组合查询增强
4. 系统验证与 benchmark 建设
5. 论文材料与 artifact 收口

下面展开每个阶段。


## 第一阶段：语言与语义重构

### 阶段目标

把现在“能跑的 keyword parser”提升为“可描述、可验证、可扩展的 query language”。

### 为什么这一阶段最优先

因为如果语言层没有形式化定义，后面无论怎么做优化器、实验，论文都容易被认为只是：

- 一个脚本接口
- 一个命令行前端
- 一个方便调参数的壳

### 需要完成的子任务

#### 1. 定义正式语法

建议新增一份文档，例如：

- `docs/query_language_spec.md`

内容至少包括：

- 终结符和非终结符
- 查询语句的 EBNF 或 BNF
- 子句顺序规则
- 可选子句和必选子句
- 非法语句示例

建议覆盖的语法骨架：

```text
QUERY :=
  EXPLAIN TARGET
  [WHERE PREDICATE_LIST]
  [AT LAYER n | AT ALL LAYERS]
  [INCLUDE NODE_LIST]
  [EXCLUDE NODE_LIST]
  [WITH PARAM_LIST]
  [COMPARE BY METRIC]
```

#### 2. 定义查询对象模型

目前 `ExplainQuery` 已经存在，但需要从“实现数据类”升级为“语言级抽象”。

建议明确这些字段：

- `target_type`
- `target_scope`
- `constraint_predicates`
- `structural_constraints`
- `execution_preferences`
- `comparison_request`
- `approximation_config`

建议做法：

- 保留现有 `ExplainQuery`
- 但拆分或增强为更清晰的结构

例如可以考虑新增：

- `TargetSpec`
- `PredicateSpec`
- `ExecutionSpec`
- `CompareSpec`

#### 3. 定义查询语义

这是本阶段最关键的部分。

建议新增语义文档，例如：

- `docs/query_semantics.md`

需要说明：

- `EXPLAIN NODE 519` 返回的对象是什么
- `EXPLAIN ALL` 的结果集合如何定义
- `WHERE FACTUAL = TRUE` 是对结果过滤，还是对执行空间约束
- `COMPARE BY COMMON_NODES` 的输出对象是什么
- `AT ALL LAYERS` 的返回结构是否带层维度
- `WITH APPROXIMATE 0.3` 是否改变语义，还是只改变执行方式

#### 4. 加入静态校验

当前 parser 主要是“读进来就转对象”。下一步需要增加 query validation。

建议新增逻辑：

- 参数范围校验
- query clause 冲突校验
- 节点列表格式校验
- 比较操作和结果类型的匹配校验

建议新增模块：

- `query_validator.py`

### 涉及文件

重点涉及：

- [slicegx_lang.py](/home/ycb/SliceGX/slicegx_lang.py:1)
- 新增 `docs/query_language_spec.md`
- 新增 `docs/query_semantics.md`
- 可选新增 `query_validator.py`

### 验收标准

本阶段完成后，至少应满足：

- 任意 query 都能给出“合法 / 非法”的明确反馈
- 语言有独立文档，不依赖读代码理解
- `ExplainQuery` 字段语义清晰
- approximate、layer、compare 等语义都有文字定义


## 第二阶段：执行计划与优化器重构

### 阶段目标

把现在的 `auto_route` 从“简单规则判断”升级成一个明确的 planner / optimizer 框架。

### 当前问题

当前系统已经有：

- parser
- executor
- `auto_route`

但还缺：

- logical plan
- physical plan
- optimization rule
- cost estimation

### 需要完成的子任务

#### 1. 引入逻辑计划层

建议在 parser 和 executor 中间加入 logical plan。

逻辑计划负责表达“用户想做什么”，而不是“系统具体怎么做”。

例如可以定义这些 logical operators：

- `TargetScan`
- `ConstraintFilter`
- `LayerScope`
- `ExplainOp`
- `CompareOp`
- `AggregatePatternOp`

建议新增模块：

- `planner/logical_plan.py`

#### 2. 引入物理计划层

物理计划负责表达“系统怎么执行”。

例如：

- `SingleNodeExactPlan`
- `MultiNodeSharedPlan`
- `MultiLayerPlan`
- `ApproximateSamplePlan`
- `CacheResumePlan`

建议新增模块：

- `planner/physical_plan.py`

#### 3. 重构 auto_route 为 optimizer

当前 `auto_route` 只依据：

- 单节点 / 多节点
- 单层 / 全层

下一步应至少纳入这些决策因子：

- 目标节点数量
- 是否跨层
- `K` 的大小
- 近邻规模
- 是否开启 approximate
- cache 是否命中
- 多个节点之间是否有重叠邻域

建议新增模块：

- `planner/optimizer.py`

#### 4. 设计轻量 cost model

初版不需要很复杂，但必须有。

建议至少估计：

- 目标数量成本
- 邻域展开成本
- 层数成本
- 采样比例带来的成本变化
- cache 命中带来的收益

初版可以先做 heuristic cost：

- `cost = a * num_targets + b * avg_subgraph_size + c * num_layers + d * K`

后续可以再用 profiling 数据拟合。

#### 5. 支持计划可解释输出

这是很重要但经常被忽略的一点。

建议增加一种调试或 explain 模式，例如：

- `EXPLAIN PLAN FOR EXPLAIN NODE 519 WITH K 6`

或内部先实现日志输出：

- 逻辑计划长什么样
- 为什么选 SS / MS / MM
- approximate 为什么开启或未开启
- cache 为什么命中或 miss

### 涉及文件

重点涉及：

- [slicegx_lang.py](/home/ycb/SliceGX/slicegx_lang.py:1)
- 可新建 `planner/` 目录
- `SliceGX.py`
- `Slice_MS.py`
- `Slice_MM.py`

### 验收标准

本阶段完成后，至少应满足：

- parser 输出不再直接进入 executor，而是先生成 plan
- 系统能打印 logical plan 与 physical plan
- `auto_route` 不再只是硬编码 if/else，而是优化器模块的一部分
- 每条 query 的执行决策有明确解释


## 第三阶段：结果模型与组合查询增强

### 阶段目标

把当前“返回 dict + 打印文本”的模式，升级成“有 schema 的结果对象 + 可组合查询”。

### 当前进展

这一阶段已经部分完成，当前已有：

- `PlanSummary`
- `ComparisonSummary`
- `ErrorSummary`
- `ExplanationResult`
- `QueryExecutionResult`
- REPL 内的最小组合能力：
  - `LET Q1 = ...`
  - `FILTER Q1 WHERE ...`
  - `RANK Q1 BY FIDELITY_PLUS`
  - `COMPARE Q1 BY FIDELITY_PLUS`
  - `COMPARE Q1 BY COMMON_NODES`

### 当前问题

当前结果主要长这样：

- `node_id`
- `nodes`
- `Fid+`
- `Fid-`
- `factual`
- `counterfactual`

这足够执行，但还不够支撑：

- query composition
- aggregation
- downstream analysis
- structured serialization

### 需要完成的子任务

#### 1. 统一结果 schema

建议定义统一的结果对象，例如：

- `ExplanationResult`
- `ExplanationResultSet`
- `ComparisonResult`
- `PatternResult`

建议新增模块：

- `result_schema.py`

字段建议包括：

- query id
- target info
- layer info
- explanation nodes
- scores
- factual / counterfactual flags
- execution metadata
- provenance / source backend

#### 2. 结果序列化

建议支持：

- JSON 输出
- 表格化输出
- 日志输出

这样后面做 benchmark 和论文图表会轻松很多。

建议至少提供：

- `--output-format text|json`

#### 3. 加入命名查询和查询组合

这是从“命令接口”迈向“查询语言”的关键一步。

当前已经实现的最小版本：

- `LET Q1 = EXPLAIN ALL WHERE FACTUAL = TRUE`
- `COMPARE Q1 BY COMMON_NODES`
- `FILTER Q1 WHERE FACTUAL = TRUE`
- `RANK Q1 BY FIDELITY_PLUS`

后续可逐步支持：

- `FILTER Q1 WHERE ...`
- `RANK Q1 BY ...`
- `SUMMARIZE Q1`

#### 4. 抽象比较与聚合操作

当前 `COMPARE BY FIDELITY_PLUS`、`COMPARE BY COMMON_NODES` 已经存在，但还偏点状。

建议把它们抽象成统一 operator：

- `RankByMetric`
- `CommonPatternSummary`
- `SupportAggregation`

### 涉及文件

重点涉及：

- [slicegx_lang.py](/home/ycb/SliceGX/slicegx_lang.py:1)
- 新增 `result_schema.py`
- 新增 `docs/result_model.md`

### 验收标准

本阶段完成后，至少应满足：

- 结果对象有统一结构定义
- 查询结果可以以 JSON 导出
- 支持最小形式的命名查询
- compare 不再只是打印逻辑，而是结果代数的一部分

当前已满足：

- 统一结果结构已初步建立
- JSON 输出已打通
- `LET / FILTER / RANK / COMPARE` 已支持最小版本
- `COMPARE` 已可作用于已保存结果集

当前尚未完成：

- `SUMMARIZE`
- 更丰富的排序/聚合操作
- 持久化 session 结果
- 单次命令模式下的复杂组合查询


## 第四阶段：系统验证与 Benchmark 建设

### 阶段目标

建立一套可以支撑论文实验的 workload 和 benchmark，而不是只靠功能演示脚本。

### 当前问题

当前的 [test_features.sh](/home/ycb/SliceGX/test_features.sh:1) 很适合做 feature demo，但不够支撑系统论文。

因为它主要回答的是：

- 功能在不在

但还没有系统回答：

- 表达能力提升了多少
- 优化器加速了多少
- approximate 的误差和收益如何
- cache 的收益如何

### 需要完成的子任务

#### 1. 设计 workload 分类

建议至少构建以下五类 workload：

- 单节点精确解释
- 多节点批量解释
- 跨层解释查询
- 约束型查询
- 聚合/比较型查询

每类 workload 至少设计 5 到 10 个代表性 query。

#### 2. 建立 benchmark query 集合

建议新增：

- `benchmarks/queries/`

例如：

- `single_node_exact.txt`
- `multi_node_shared.txt`
- `layered_queries.txt`
- `approximate_queries.txt`
- `compare_queries.txt`

#### 3. 加入系统级指标采集

建议记录：

- parsing time
- planning time
- execution time
- cache hit rate
- explanation count
- result size
- approximate ratio
- plan type

#### 4. 做 ablation 支持

建议加入可控开关：

- 关闭 optimizer
- 关闭 cache
- 关闭 approximate
- 强制 SS / MS / MM

这样实验时可以比较：

- optimized vs naive
- cache vs no cache
- approximate vs exact

#### 5. 让测试脚本分层

建议把现在的 `test_features.sh` 拆成：

- `scripts/test_features.sh`
- `scripts/run_benchmarks.sh`
- `scripts/run_ablation.sh`

### 涉及文件

重点涉及：

- [test_features.sh](/home/ycb/SliceGX/test_features.sh:1)
- 新增 `benchmarks/`
- 新增 `scripts/`
- `slicegx_lang.py` 中增加 metrics/logging 支持

### 验收标准

本阶段完成后，至少应满足：

- 有一组固定 benchmark query
- 每条 query 都能产出结构化指标
- 能跑 ablation
- 能比较 optimized plan 与 naive baseline

## 风险与注意事项

### 风险 1：过早加太多语言 feature

如果继续快速加关键字，而不补 planner / semantics，系统会越来越像：

- 复杂 CLI

而不是：

- declarative engine

### 风险 2：优化器没有可解释性

如果 optimizer 只是更复杂的 if/else，但没有 plan、cost、reasoning 输出，论文说服力会不够。

### 风险 3：结果模型不统一

如果不同 backend 各自返回不同 dict，后面比较、聚合、benchmark 都会非常痛苦。

### 风险 4：实验只做“能跑”

功能演示不是系统评估。  
一定要尽早让系统输出结构化指标。

## 下一步最推荐先落地的三件事

如果你想要一个最小但正确的起步顺序，我最推荐先做下面三件事。

### 1. 写语言规范和语义文档

这是最便宜、收益最高的一步。  
它会直接帮助你：

- 统一团队理解
- 减少后续接口反复改
- 为论文打基础

### 2. 把 auto_route 重构成 optimizer 雏形

哪怕第一版只是 rule-based，也要把：

- 输入
- plan
- 决策规则
- 输出

这条链搭起来。

### 3. 统一结果 schema 并支持 JSON 导出

没有统一结果对象，后面的 benchmark、聚合、ablation 都很难做稳。


## 最终结论

基于现有系统，下一步最重要的不是继续往 DSL 里堆 feature，而是把系统的四层骨架补齐：
